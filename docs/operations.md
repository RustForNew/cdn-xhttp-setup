# Эксплуатация

Для первого запуска начните с [README](../README.md). Здесь собраны настройки CDN, повторные команды и диагностика.

## Настройки существующего CDN

Нужны два разных домена:

- **Origin-домен** указывает на IP вашего VPS через A или AAAA. Удалите лишние записи с другими адресами.
- **CDN-домен** используется в клиентских ссылках. Его CNAME указывает на адрес, выданный CDN-провайдером, а сертификат должен быть выпущен и подключён к CDN.

Программа настраивает VPS и выпускает сертификат origin. DNS-записи, CDN-ресурс и сертификат CDN-домена настраиваются у соответствующих провайдеров.

Для Yandex Cloud CDN проверьте:

| Настройка | Значение |
| --- | --- |
| Источник | Origin-домен |
| Протокол до источника | HTTPS |
| Host источника | Origin-домен |
| SNI источника | Origin-домен |
| Доступ пользователей | Включён |
| HTTP-методы | GET, HEAD, OPTIONS |
| Кеширование CDN и браузера | Выключено |
| Игнорирование параметров запроса и Cookie | Выключено: параметры и Cookie сохраняются |
| Сжатие, сегментация, экранирование источника (shielding) | Выключены |
| Заголовки запроса `X-Cache` и `X-Data-N` | Передаются без удаления и замены |
| Статический ответ на OPTIONS | Не задан: запрос доходит до origin |
| Следование перенаправлениям origin | Выключено |

Host и SNI сообщают серверу, к какому домену идёт запрос; здесь оба должны совпадать с origin-доменом. Данные клиента идут в заголовках `X-Data-0`, `X-Data-1`… запросов OPTIONS без тела, padding — в заголовке `X-Cache`. Тело запроса не используется: Yandex CDN отвечает HTTP 413 на любое тело GET, HEAD и OPTIONS, а POST не предлагает. WebSocket не требуется.

Официальная справка Yandex Cloud: [SNI](https://yandex.cloud/en/docs/cdn/operations/resources/configure-server-name), [HTTP-методы](https://yandex.cloud/en/docs/cdn/operations/resources/configure-http), [кеширование](https://yandex.cloud/en/docs/cdn/operations/resources/configure-caching), [параметры CDN-ресурса](https://yandex.cloud/en/docs/cdn/api-ref/Resource/create), [типичные ошибки](https://yandex.cloud/ru/docs/cdn/troubleshooting).

### Ограничения Yandex CDN

Измерено 01.10.2026 через настоящий edge Yandex CDN:

- заголовки запроса до 32 КБ проходят; один пакет этой схемы — около 23 КБ заголовков;
- около 200 запросов в секунду с одного IP проходят без ошибок; один отправитель делает около 100;
- ответ, в котором 60 секунд нет ни одного байта, edge закрывает. Долгая отправка без ответа сервера дольше ~60 секунд (≈90 МБ при 12 Мбит/с) обрывается, и приложение переподключается;
- изредка edge отвечает 502 на часть запросов, и сессия пересоздаётся.

Результат схемы на том же пути: upload ≈12 Мбит/с, download ≈75 Мбит/с. Для сравнения: OPTIONS по 4 КиБ с паузой 5 мс — ≈5,8 Мбит/с, GET по 1,5–6 КБ с паузой 10–30 мс — ≈1,6 Мбит/с. Скорость зависит от сети, edge и нагрузки; это не гарантия для другого ресурса.

После изменений дождитесь их применения и повторите `check`. HTTPS-запросы проверки должны получать ответ напрямую, без перенаправления на другой адрес.

## Порты и требования к VPS

Используйте отдельный VPS без действующих сайтов на портах 80/443. Нужны root или пользователь с sudo. VPS должен иметь доступ к репозиториям Ubuntu, GitHub и Let's Encrypt.

Откройте порты в панели VPS-провайдера:

| Сервер | Входящие TCP-порты |
| --- | --- |
| Origin | SSH-порт, обычно 22; 80; 443 |
| Exit, если используется | SSH-порт; 80; 10443 от IP origin |

TCP 80 нужен для выпуска и дальнейшего продления сертификатов. Порты 8003/8004 работают только внутри origin и не открываются наружу.

Если UFW уже включён, программа добавляет правила для SSH и нужных портов. Выключенный UFW не включается. Правила в панели провайдера программа не меняет, существующие широкие разрешения не сужает.

## Повторный запуск

Сохраните `deployment.json`: в нём настройки и UUID доступа. Не передавайте этот файл посторонним.

Запуск без аргументов при наличии `deployment.json` открывает меню управления. Если файла нет, мастер запрашивает SSH-доступ к origin и проверяет свою серверную установку: при её наличии загружает настройки и UUID и открывает меню. Локальный `deployment.json` для восстановления не обязателен. Для другого VPS выберите подключение к другому origin в меню либо отдельный `--config`.

Установка 0.2.0 сохраняет полные настройки на сервере. Из версии 0.1.x также восстанавливаются домены, путь и UUID, но email сертификата и SSH-логин/порт exit нужно подтвердить отдельно. При наличии локального файла сохраняются его название и профиль; без него используются `CDN XHTTP` и `fast`, которые можно изменить в меню.

Для новой установки выбирается мост (два сервера) или один VPS. Пароль запрашивается рядом с IP и SSH-логином каждого сервера; Enter вместо пароля выбирает SSH-ключ/агент. Для пользователя без root отдельно запрашивается пароль sudo. Пароли находятся только в памяти до завершения запуска. Все вопросы подтверждения принимают Y/N без учёта регистра, а также yes/no и да/нет; неизвестный ответ повторяет вопрос.

Мастер не спрашивает технические параметры XHTTP: для новой конфигурации используются `fast` и `/api-test`. Повторная установка сохраняет параметры загруженного файла, включая `original`, если он был задан вручную.

Windows CMD:

```bat
run.cmd deploy --config deployment.json
run.cmd check --config deployment.json
run.cmd link --config deployment.json
run.cmd manage --config deployment.json
run.cmd plan --config deployment.json --output preview
```

На Linux замените `run.cmd` на `bash run.sh`.

- `deploy` — повторная установка с сохранением UUID, затем выдача ссылок и информационная проверка подключения.
- `link` — выдача ссылок по актуальной серверной установке, затем информационная проверка.
- `check` — то же, что `link`, но с кодом завершения 2, если туннель не подтверждён.
- `manage` — меню управления существующими настройками или восстановление по SSH при отсутствии локального файла.
- `plan` — создание скриптов и конфигов для просмотра без подключения к VPS.

В меню существующей установки доступны выдача ссылок, изменение количества UUID, доменов и других настроек, повторная установка и подключение к другому VPS. Перед изменениями и повторной выдачей ссылок серверная копия перечитывается по SSH, чтобы не затереть более новые настройки и не выдать отозванные UUID из устаревшего локального файла. `check` и `link` также требуют SSH-доступ к origin, но не переустанавливают VPS. При отказе SSH ссылки не выдаются: список действующих UUID не подтверждён. После успешной установки дополнительное SSH-чтение не требуется. Команда `repair-edge` прежних версий оставлена скрытым синонимом `link`: подбирать адрес CDN больше не нужно.

### Количество UUID и настройки

Увеличение количества ссылок сохраняет все прежние UUID и добавляет новые. Уменьшение сохраняет первые UUID и удаляет последние: прежние ссылки удалённых пользователей теряют доступ. Первый UUID сохраняется, поскольку в схеме двух VPS он также используется на участке origin → exit. Допустимо от 1 до 1000 UUID.

Для смены имени, доменов origin/CDN/exit, email сертификата, пути, профиля или ключа padding используйте настройки существующей установки. Программа не создаёт DNS-записи и не меняет ресурс CDN. До применения новых доменов подготовьте DNS и сертификат CDN, согласуйте Host/SNI источника в панели провайдера. Для origin-домена должен быть доступен HTTP-01 на TCP 80; путь XHTTP и padding должны совпадать у сервера и клиента.

Профили `fast` и `original` отличаются паузой отправки 10/30 мс; серверные параметры одинаковы. После изменения настроек заново импортируйте выданные ссылки или клиентские JSON. При успешном обновлении VPS локальная конфигурация сохраняется и ссылки выдаются даже при отказе последующей проверки: исправьте сетевую причину и повторите `check`.

## Проверка подключения

Адрес подключения в ссылках и клиентских JSON — всегда CDN-домен на порту 443; конкретный edge выбирает DNS провайдера CDN. Программа не ищет и не закрепляет IP edge, а в панели CDN IP не указывается: там остаются домен источника, его Host/SNI и выданный провайдером DNS target.

Ссылки записываются сразу после установки или SSH-чтения актуальных настроек. Затем программа проверяет путь с вашего компьютера:

1. `OPTIONS /cdn-check` на CDN-домен без тела, с 16 КиБ случайных данных в заголовках `X-Data-N`, как пакет XHTTP. Проверяются сертификат, метод, отсутствие кеша и перенаправлений и совпадение SHA256 заголовков на origin.
2. Временный Xray закреплённой версии с опубликованным профилем первого UUID подключается к CDN-домену. Через VLESS проверяются отправка 1 000 000 байт на origin, загрузка с проверкой SHA256 и внешний IP origin/exit. Бинарник Xray скачивается с GitHub и сверяется по SHA256.

Проверка только информирует. Если она не прошла — например, нет доступа к GitHub, сеть компьютера блокирует CDN или CDN ещё применяет настройки, — ссылки всё равно выданы, а программа выводит предупреждение. Состояние вашего VPN, proxy и сетевых адаптеров программа не меняет; при включённом VPN проверка может идти через него.

В `result/status.json` смотрите `endpoint_verified`, `vless_tunnel_verified`, `note` и `checks`. Пока проверка не завершена, статус отрицательный. HTTP 200 от `/cdn-check` сам по себе не означает, что VPN работает: решающий признак — `vless_tunnel_verified`.

## Второй сервер

Если нужен отдельный сервер для выхода в интернет, ответьте «да» на вопрос мастера об exit. Укажите его IP, SSH-логин, порт и отдельный exit-домен с A/AAAA-записью на этот VPS. Origin и exit должны использовать одну семью IP-адресов: оба IPv4 или оба IPv6.

На exit нужны Ubuntu 22.04/24.04 и открытые порты из таблицы выше. Сертификат его домена программа выпустит автоматически. Клиентская ссылка использует CDN-домен в адресе, SNI и Host, а сайты будут видеть IP exit.

Сначала настраивается exit, затем origin. Если настройка origin завершится ошибкой, установленный exit останется на месте. Исправьте причину и повторите `deploy` с тем же файлом настроек.

## Что меняется на сервере

Программа проверяет версию Ubuntu, архитектуру, systemd, порты и существующие настройки. Она не заменяет изменённый `nginx.conf` или посторонние сайты. Стандартный сайт Nginx отключается только после проверки, что его файл не менялся.

| Путь или служба | Назначение |
| --- | --- |
| `/opt/cdn-xhttp/xray` | Отдельный бинарник Xray |
| `/etc/cdn-xhttp/config.json` | Серверный конфиг, права root:nogroup 0640 |
| `/etc/cdn-xhttp/deployment.json` | Данные для распознавания повторной установки |
| `/etc/cdn-xhttp/setup.json` | Полные настройки и UUID для восстановления, права 0600 |
| `/etc/cdn-xhttp/tls/` | Копии сертификата exit |
| `cdn-xhttp.service` | Xray от пользователя nobody |
| `cdn-xhttp-health.service` | Проверка OPTIONS на origin |
| `/opt/cdn-xhttp/health.py` | Диагностическая служба |
| `/etc/nginx/sites-available/cdn-xhttp.conf` | HTTPS и передача XHTTP |
| `/var/www/cdn-xhttp-acme` | Проверка домена при выпуске сертификата |
| `/etc/letsencrypt/renewal-hooks/deploy/cdn-xhttp.sh` | Обновление служб после продления сертификата |
| `/var/backups/cdn-xhttp/` | Резервные копии файлов проекта |
| `/var/lib/cdn-xhttp/certificate-owner.json` | Владелец сертификатов завершённой установки, записывается в её конце |
| `/var/lib/cdn-xhttp/certificates/` | Записи о сертификатах, выпущенных программой; запись домена появляется только после выпуска его сертификата |

Сертификаты продлевает `certbot.timer`. После продления на origin перечитывается конфиг Nginx, на exit обновляются копии сертификата и перезапускается Xray.

## Если установка прервалась

Для обновления существующей установки перед изменением VPS создаётся `deployment.pending.json`. Если, например, exit обновился, а origin — нет, не удаляйте этот файл: в меню появится пункт **6 — продолжить незавершённое изменение**. Он повторит применение с теми же UUID. Основной `deployment.json` обновится и pending удалится только после успеха на всех узлах, до выдачи ссылок. Для другого сервера используйте отдельный `--config`, пока изменение не завершено.

Pending создаётся только после проверки, что изменение можно применить: смена схемы (добавление или удаление exit) или перенос роли на другой IP отклоняются до записи файла и до запроса паролей. Если такой невыполнимый pending остался от версии 0.3.x, пункт 6 сообщит причину и предложит удалить его; основной `deployment.json` при этом не меняется.

Pending, основной файл и резервные копии содержат UUID доступа. При переносе программы в новую папку сохраняйте pending вместе с основным файлом; восстановление только по SSH к origin не знает о ещё не завершённом изменении exit.

Перед заменой своих файлов программа сохраняет резервную копию, доступную только root. При обычной ошибке восстанавливаются файлы проекта и прежнее состояние служб. При обрыве SSH, отключении питания или принудительной остановке проверьте VPS вручную: автоматическое восстановление не гарантируется.

Установленные пакеты, выпущенные сертификаты и добавленные правила UFW остаются. Сертификат, выпущенный программой, используется повторно после исправления ошибки, даже если при повторе исправлен CDN-домен. Если первая установка прервалась до выпуска сертификата, она не оставляет претензий на домен: повтор с исправленными CDN- или origin-доменом не блокируется. Сертификат того же домена, выпущенный не этой программой, по-прежнему не используется.

Если SSH-чтение установки не удалось, программа показывает причину с сервера: например, неверный пароль sudo, идущую установку (`Another cdn-xhttp deployment is running`) или неполную установку. Пароли в этом тексте скрываются.

Для ручного восстановления используйте нужную копию из `/var/backups/cdn-xhttp/` и возвращайте только необходимые файлы с сохранением прав. Резервные копии содержат данные доступа; не публикуйте их.

## Диагностика

Начните с `check` на своём компьютере. Для проверки VPS подключитесь по SSH и выполните на origin:

```bash
sudo systemctl status cdn-xhttp cdn-xhttp-health nginx --no-pager
sudo nginx -t
sudo runuser -u nobody -- /opt/cdn-xhttp/xray run -test -config /etc/cdn-xhttp/config.json
sudo journalctl -u cdn-xhttp -u cdn-xhttp-health -u nginx --since '10 minutes ago' --no-pager
sudo systemctl status certbot.timer --no-pager
```

На exit проверьте `cdn-xhttp`, `certbot.timer` и доступ к порту 10443 от origin.

| Проблема | Что проверить |
| --- | --- |
| Не выпускается сертификат | A/AAAA домена и доступность TCP 80 |
| Предупреждение о DNS из 198.18.0.0/15 | Локальный VPN в режиме fake-ip/TUN подменяет ответы DNS; установка продолжается, а VPS сам сверяет A/AAAA со своим IP перед выпуском сертификата |
| Ошибка сертификата CDN | Выпуск и подключение сертификата в панели CDN |
| CDN отвечает 502/504 | HTTPS origin, Host/SNI и доступ к порту 443 |
| `check` сообщает об изменённых заголовках `X-Data` | Разрешение OPTIONS, отключение кеша и передачу заголовков `X-Cache`/`X-Data-N` |
| CDN отвечает 413 | Клиент или проверка прежней версии с телом OPTIONS; обновите программу, повторите установку и заново импортируйте ссылки |
| Отправка обрывается примерно через минуту | Ограничение CDN на 60 секунд без ответа; приложение переподключается |
| Туннель не подтверждён, хотя `/cdn-check` отвечает | Авторизацию VLESS, сохранение OPTIONS/padding, XHTTP-путь, связь origin → exit и доступ компьютера к GitHub для загрузки Xray |
| Проверка проходит только с включённым VPN | Доступность CDN из сети компьютера без VPN; проверьте в клиентском приложении |
| `check` успешен, но ссылка не работает в другом клиенте | Поддержку и сохранение XHTTP extra и внешнего `mode=packet-up`, сеть клиента и актуальность ссылки |
| Внешний IP отличается от адреса VPS | NAT или дополнительный выход; такая схема не поддерживается автоматической проверкой |

`check` проверяет полный VLESS-путь с этого компьютера через его обычный маршрут. Он не измеряет скорость и не подтверждает совместимость интерфейса импорта конкретного приложения. После импорта ссылки проверьте работу в клиенте.

Коды завершения: `0` — успех, ссылки выданы (у `deploy` и `link` — независимо от результата проверки); `1` — ошибка ввода, SSH или установки; `2` — только у `check`: ссылки выданы, но туннель с этого компьютера не подтверждён; `130` — прервано пользователем. Причину смотрите в свежем `status.json`.

## Обновление локального установщика

Автоматическая проверка выпусков и перенос старых копий описаны в [инструкции по обновлению](updating.md). Обновление программы не применяет настройки к VPS и не пересоздаёт UUID.
