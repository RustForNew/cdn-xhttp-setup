# Архитектура и контракты

Техническая справка для разработчиков. Для установки достаточно [основной инструкции](../README.md).

## Компоненты

Программа запускается на Windows или Linux и настраивает VPS по SSH через Paramiko. CDN и DNS должны быть готовы заранее. Создание облачных ресурсов в программу не входит.

| Модуль | Назначение |
| --- | --- |
| `config.py` | Проверка и сохранение параметров |
| `render.py` | Конфиги Xray, Nginx и VLESS-ссылки |
| `remote.py` | Передача установочного скрипта, восстановление настроек по SSH и запуск через root/sudo |
| `health.py` | Предварительная проверка HTTPS и передачи OPTIONS |
| `edge.py` | Подбор CDN edge и проверка VLESS-туннеля |
| `edge_network.py` | Обнаружение Ethernet, привязка сокетов и временный TCP relay |
| `edge_runtime.py` | Проверенный временный Xray, SOCKS и HTTPS-проверки |
| `cli.py` | Мастер установки, управление UUID/настройками и команды |

## Конфигурация

`deployment.json` использует схему версии 1. Неизвестные поля отклоняются. SSH-пароли и пароли sudo не сохраняются.

- `name`: название ссылок, 1–80 символов без управляющих символов.
- `uuids`: от 1 до 1000 уникальных UUID — идентификаторов доступа. Мастер создаёт их случайным образом.
- `uuid`: первый UUID; конфиги с единственным полем `uuid` также поддерживаются.
- `profile`: `fast` или `original`, меняет интервал отправки клиента. Новый мастер всегда выбирает `fast`; ручные конфигурации и повторная установка сохраняют выбранное значение.
- `connect_address`: необязательный публичный IPv4/IPv6 выбранного CDN edge. Отсутствие поля совместимо с прежними конфигурациями; перед обычной выдачей ссылок адрес выбирается заново с проверкой сети.

Пароли передаются из мастера в установку отдельно от конфигурации, только в памяти. Для двух серверов данные доступа собираются до начала изменений на любом VPS. Установка по-прежнему выполняется в порядке exit → origin. Подтверждения Y/N повторяют вопрос при неизвестном ответе; `y` и `n` поддерживаются без учёта регистра.

`run.cmd` и `run.sh` используют общий `bootstrap.py`. Он создаёт локальное `.venv` и устанавливает зависимости при первом запуске, изменении метаданных пакета или переносе папки проекта. Исправное окружение при повторном запуске используется без повторной установки зависимостей.

Повторная установка использует сохранённые UUID. При увеличении их количества новые UUID дописываются в конец; при уменьшении удаляются последние, первый UUID сохраняется. Все оставшиеся UUID добавляются в конфиг сервера; несколько ссылок получают номера в названии. Это отдельные учётные данные без индивидуальных квот трафика.

Существующая установка обнаруживается через SSH к origin. Локальный JSON служит удобной копией настроек. При восстановлении, перед изменением работающей установки и повторной выдачей ссылок сверяются серверные данные. После успешного deployment используются только что применённые настройки, без дополнительного SSH-чтения. Потеря локального файла не является основанием для генерации новых UUID. Смена количества пользователей и настроек применяется до повторной сетевой проверки; если после успешного серверного изменения подбор edge не прошёл, локальная конфигурация всё равно сохраняет применённые настройки.

На сервере `/etc/cdn-xhttp/deployment.json` остаётся маркером установки, а `/etc/cdn-xhttp/setup.json` содержит полную конфигурацию начиная с версии 0.2.0. Восстановление сверяет эти данные с фактическим Xray-конфигом. Конфиг origin в формате версий до 0.3.1 включительно (uplink в теле OPTIONS) тоже распознаётся, как и при сверке перед обновлением; программа сообщает, что ссылкам текущей версии нужна повторная установка сервера с теми же настройками и UUID. Для версии 0.1.x настройки восстанавливаются из маркера и Xray; отсутствующие email и SSH-поля exit запрашиваются, имя и профиль берутся из локального файла либо получают значения `CDN XHTTP` и `fast`.

Изменение существующей установки до первого удалённого обновления записывает локальный `deployment.pending.json` с `target` и `previous`. Основной файл сохраняет прежнее состояние до успеха на всех VPS. Повтор использует тот же набор UUID и ожидаемое прежнее состояние; изменение серверной конфигурации после чтения останавливает перезапись. После успешного применения основной файл обновляется, pending удаляется, затем запускается проверка CDN.

## Схемы подключения

```text
Один VPS: клиент → CDN → origin → интернет
Два VPS:  клиент → CDN → origin → exit → интернет
```

Origin — сервер, принимающий трафик от CDN. Exit — необязательный второй сервер для выхода в интернет.

Клиент подключается к выбранному CDN edge на порту 443. В VLESS URI и `client.json` меняется только адрес TCP-соединения; Host и TLS SNI равны CDN-домену, проверка сертификата включена. При отсутствии `connect_address` renderer сохраняет доменное подключение для совместимости и автономного плана. CDN обращается к origin по HTTPS. Nginx на origin завершает TLS и передаёт XHTTP в Xray на `127.0.0.1:8003`.

В режиме одного VPS Xray отправляет трафик напрямую через `freedom`. В режиме двух VPS origin соединяется с exit по VLESS TCP + TLS + `xtls-rprx-vision` на порту 10443. Для TLS используется exit-домен, для авторизации — первый UUID. Резервного прямого выхода с origin нет. Сертификаты CDN, origin и exit независимы.

Оба VPS в двухсерверном режиме должны использовать одну семью IP-адресов. Все A/AAAA-записи origin и exit должны совпадать с указанным адресом соответствующего VPS. Автоматическая настройка NAT не поддерживается.

## XHTTP и отправка данных

Yandex Cloud CDN не предлагает POST и отвечает HTTP 413 на любое тело запроса GET, HEAD или OPTIONS. Поэтому данные клиента (uplink) идут в заголовках OPTIONS без тела: каждый пакет до 16 КиБ кодируется base64url и делится на заголовки `X-Data-0`, `X-Data-1`… по 4096 символов. Вместе с padding это около 23 КБ заголовков на запрос. Ответы сервера (downlink) идут обычным потоком GET.

Параметры клиента (`extra` в ссылке и `xhttpSettings.extra` в `client.json`, профиль `fast`):

```json
{
  "xPaddingObfsMode": true,
  "xPaddingKey": "dc",
  "xPaddingHeader": "X-Cache",
  "xPaddingMethod": "tokenish",
  "xPaddingPlacement": "queryInHeader",
  "xPaddingBytes": "100-1000",
  "scMaxEachPostBytes": 16384,
  "scMinPostsIntervalMs": 10,
  "uplinkDataPlacement": "header",
  "uplinkChunkSize": 4096,
  "uplinkHTTPMethod": "OPTIONS"
}
```

`mode: packet-up` задаётся в `xhttpSettings` и отдельным параметром ссылки `mode`, вне `extra`: ядро заменяет mode из extra внешним полем. XMUX и `scMaxConcurrentPosts` не задаются. TLS проверяет сертификат CDN-домена, ALPN — `h2`, `http/1.1`, отпечаток TLS-клиента — `firefox` (`fp=firefox` в ссылке).

Профиль `fast` задаёт паузу между пакетами 10 мс, `original` — 30 мс; остальные поля одинаковы. Ноль не используется: [Xray трактует его как 30 мс](https://github.com/XTLS/Xray-core/blob/v26.9.9/transport/internet/splithttp/config.go). При паузе 10 мс один отправитель делает около 100 запросов в секунду.

Сервер (inbound origin, `xhttpSettings.extra`) использует те же параметры padding и `xPaddingBytes`, а также `scMaxEachPostBytes: 1000000`, `scMaxBufferedPosts: 64` и `serverMaxHeaderBytes: 65536`: без последнего Xray отвергает пакет в заголовках больше ~8 КиБ. Размещение uplink на сервере не задаётся: умолчание Xray `auto` читает заголовки, cookie и тело, поэтому клиенты прежних версий с телом OPTIONS до 1 000 000 байт сервером не отвергаются (их отвергает сам Yandex CDN). [Обработка XHTTP](https://github.com/XTLS/Xray-core/blob/v26.9.9/transport/internet/splithttp/hub.go).

Путь по умолчанию — `/api-test`. Параметры padding совпадают на клиенте и сервере; CDN должен сохранять заголовки запроса `X-Cache` и `X-Data-N`.

Nginx origin принимает XHTTP только по `location ^~ /api-test/`; сам `/api-test` и посторонние пути отвечают 404, поэтому `/api-testX` не попадает в Xray. OPTIONS заменяется на POST только для XHTTP (`map` и `proxy_method`): Xray сам отвечает на голый OPTIONS и данных из него не читает. К Xray Nginx ходит через `upstream cdn_xhttp_origin` с `keepalive 64`, `keepalive_requests 100000`, `keepalive_timeout 120s`, HTTP/1.1 и пустым `Connection`. Без upstream keepalive каждый из ~100 запросов в секунду открывает новое loopback-соединение, их TIME_WAIT заполняют `nf_conntrack`, и узел отбрасывает новые соединения CDN (edge отвечает 502). В HTTPS-сервере заданы `keepalive_requests 100000` и `keepalive_timeout 300s`: Nginx 1.18 по умолчанию закрывает клиентское соединение после 100 запросов, и CDN переподключался бы каждую секунду.

Буферизация запросов и ответов и кеш на XHTTP-location выключены, таймауты — 3600 секунд. Буферы заголовков (`client_header_buffer_size 64k`, `large_client_header_buffers 8 128k`) вмещают пакет в заголовках; старые HTTP/2-директивы оставлены для Nginx 1.18 и могут вызывать предупреждения на более новых версиях. Лимит тела 2 MiB сохранён для клиентов прежних версий.

VLESS-ссылка содержит параметры в JSON-поле `extra` с URL-кодированием. Если клиент теряет параметры при импорте, можно использовать полный `client.json`. Клиентские ядра Xray 26.3.27, 26.7.11 и 26.9.9 поддерживают uplink в заголовках; ядро без `uplinkDataPlacement` не подключится. [Описание формата VLESS URI](https://github.com/XTLS/Xray-core/discussions/716).

Замер 01.10.2026 через настоящий edge Yandex CDN: upload ≈12 Мбит/с, download ≈75 Мбит/с. Для сравнения на том же пути: OPTIONS по 4 КиБ с паузой 5 мс — ≈5,8 Мбит/с, GET по 1,5–6 КБ с паузой 10–30 мс — ≈1,6 Мбит/с. Ограничения CDN описаны в [эксплуатации](operations.md#ограничения-yandex-cdn).

## Проверка соединения и выбор edge

Путь `/cdn-check` направляет OPTIONS в диагностическую службу на `127.0.0.1:8004`. Служба возвращает метод, длину и SHA256 полученного тела. Проверка отправляет случайные 4 байта и 1 000 000 байт, сверяет ответ и сертификат TLS. Кеширование и перенаправления не допускаются.

Проверка OPTIONS отсеивает неподходящие адреса, но сама по себе не подтверждает VLESS. Подбор выполняется автоматически после установки VPS, при `check`, `link` и `repair-edge`; отдельное действие пользователя для первого подбора не требуется.

Кандидаты включают ранее сохранённый адрес, текущие A/AAAA CDN-домена, 53 встроенных IPv4-кандидата Yandex и ограниченную выборку публичных IPv4 из опубликованного списка Yandex CDN. Встроенный список проверяется перед выборкой диапазонов, доступен при отказе загрузки списка и проходит общую дедупликацию; сохранённый адрес и DNS сохраняют приоритет. Ни один встроенный IP не считается рабочим без полной проверки. Программа не перебирает всю сеть провайдера и не гарантирует, что любой адрес из списка обслуживает конкретный ресурс. Решение принимается по фактической проверке с CDN-доменом в SNI/Host.

Сначала используется обнаруженный физический Ethernet с IPv4. Сокеты внешнего TCP relay закреплены за его исходным адресом и интерфейсом; Xray подключается только к loopback relay. IPv6-кандидаты проверяются через системный маршрут. Если проводного интерфейса нет или ни один кандидат не проходит проверку, явно объявляется переход на системный маршрут. Программа не отключает действующий VPN; успех через системный маршрут может зависеть от него и не является доказательством доступности из Ethernet.

Для кандидата запускается временный Xray закреплённой версии с проверенным бинарником, исходными XHTTP-параметрами и первым UUID актуальной установки. Проверка подтверждает общий сетевой путь; отдельный туннель для каждого UUID не запускается. Перед обычной повторной выдачей CLI получает список UUID по SSH, чтобы не экспортировать отозванные доступы из устаревшего локального файла. Локальный SOCKS listener требует пароль. Через VLESS проверяются передача данных с хешем и внешний IP, равный IP origin либо exit. NAT с иным внешним адресом не поддерживается. Временный процесс и его файлы удаляются после проверки.

`select_edge()` не изменяет конфигурацию или VPS. При успехе он возвращает выбранный `connect_address`, `endpoint_verified`, `vless_tunnel_verified`, маршрут `ethernet`/`default` и результаты `checks`. CLI сохраняет адрес и формирует ссылки только после успешного полного пути. При отказе записывается отрицательный `status.json`; ранее сформированные ссылки не перезаписываются и не получают подтверждения новой проверки. Автономный `plan` остаётся непроверенным.

Положительный `vless_tunnel_verified` подтверждает проверенный путь в момент запуска. Длительную работу, скорость, другие сети и импорт в конкретное клиентское приложение нужно оценивать отдельно.

## Версия Xray

По умолчанию закреплена [26.9.9](https://github.com/XTLS/Xray-core/releases/tag/v26.9.9). Установщик скачивает подходящий бинарник для amd64/arm64 и сверяет SHA256 с официальным файлом контрольных сумм `.dgst`. Сторонние установочные скрипты не запускаются. Автоматического обновления Xray нет.

Конфигурации прежних версий с `xray_version: "26.5.9"` (локальный `deployment.json`, pending- и backup-файлы, серверный `setup.json`) загружаются: значение заменяется на 26.9.9, и следующая установка ставит эту версию. Другие версии отклоняются.

## Обновления локальной программы

Автоматическая проверка стабильного GitHub-выпуска отделена от SSH и применения серверных настроек. Подтверждённое пользователем обновление проверяет официальный release ZIP, SHA256 и манифест файлов программы, создаёт проверенную резервную копию и готовит отдельную соседнюю папку. Пользовательские файлы и их содержимое сохраняются; `.venv` в новой папке создаётся заново. Исходная установка остаётся доступной при ошибке. Изменённый код, конфликт пользовательского файла с новым файлом программы и Git checkout требуют ручного обновления.

Артефакт выпуска содержит `release-manifest.json`: версию и SHA256 каждого файла программы, кроме самого манифеста. Манифест не содержит пользовательских конфигураций. Программа не отправляет конфиги, UUID, SSH-пароли или содержимое пользовательских файлов в GitHub. Порядок эксплуатации и миграция старых выпусков — в [обновлении программы](updating.md).
