# Тестирование

## Локальные проверки

Из папки проекта, в отдельном Python-окружении:

```bash
python -m pip install -e . pytest cryptography
python -m pytest -q
python -m compileall -q cdn_xhttp
```

Тесты проверяют ввод данных, формирование ссылок, параметры одного и двух серверов, уникальные UUID, сохранение файлов, SSH-установщик и обработку ошибок. Проверка HTTP использует локальную службу и сверяет полученные данные по SHA256. Успех тестов с заглушками сетевых вызовов не доказывает доступность CDN.

При изменениях мастера и восстановления проверяйте следующие контракты:

- Первый новый запуск запрашивает origin SSH, распознаёт существующую установку и восстанавливает её без локального JSON. Новая установка продолжает мастер выбора одного/двух VPS.
- Пароли передаются нужному VPS только в памяти; не попадают в файлы и сообщения об ошибках. Неизвестный ответ Y/N и неверное поле повторяют соответствующий вопрос.
- Повторная выдача ссылок сохраняет UUID; увеличение количества добавляет UUID, уменьшение удаляет последние только после предупреждения. Первый UUID не меняется.
- Перед изменениями и повторной выдачей ссылок загружается актуальная серверная копия. Если другая папка программы отозвала UUID, они не экспортируются из старого локального файла. При отказе SSH новые подтверждённые ссылки не выдаются. Чужая либо изменившаяся после чтения конфигурация не перезаписывается.
- Отмена и прерывание не теряют сохранённые настройки. Частично применённое изменение двух VPS можно продолжить с теми же UUID; успешное обновление серверов сохраняется локально даже при последующей недоступности edge.
- Нормальные команды `deploy`, `check`, `link` и `repair-edge` выдают файлы только после полного VLESS-подтверждения. Неуспех записывает отрицательный статус, сохраняя прежние файлы; `plan` явно остаётся непроверенным.

Для edge-подбора проверяйте наличие всех 53 встроенных кандидатов при недоступном списке сетей, дедупликацию и их приоритет перед ограниченной выборкой диапазонов. Также проверяйте порядок кандидатов, предел выборки сетей, привязку исходящего сокета к физическому Ethernet, явный переход на системный маршрут, сохранение SNI/Host и XHTTP mode, отказ при неверном сертификате, хеше, UUID или выходном IP. Временный Xray и TCP relay должны завершаться как при успехе, так и при ошибке; проверка не должна менять адаптеры или системный VPN.

SSH и внешние сетевые вызовы в регрессионных тестах заменяются заглушками либо локальными службами. Тесты запуска проверяют повторное использование окружения, обновление зависимостей при изменении метаданных и обработку ошибок подготовки.

Часть тестов установщика требует Bash. На Windows они используют Git Bash при его наличии; пропущенные тесты видны в отчёте pytest.

## Проверка настоящим Xray

Скачайте [официальный Xray 26.9.9](https://github.com/XTLS/Xray-core/releases/tag/v26.9.9) для своего компьютера и сверьте SHA256 архива с файлом `.dgst`. Укажите путь к распакованному бинарнику:

```bash
python tests/smoke_xray.py --xray /path/to/xray
```

На Windows укажите путь к `xray.exe`.

Сценарий сначала проверяет сгенерированные конфиги клиента и origin командой `xray run -test`, затем запускает Xray-клиент, origin и при необходимости exit во временных папках на локальных портах. Он проверяет четыре сочетания: один/два сервера и `fast`/`original`. 3 МиБ отправки сверяются по SHA256. Соединение с exit использует TLS + Vision.

Локальный HTTP-прокси заменяет CDN и Nginx: сохраняет padding, преобразует OPTIONS в POST и, как Yandex CDN, отвечает 413 на OPTIONS с телом. Тест требует, чтобы каждый пакет отправки шёл в заголовках `X-Data-N` не длиннее 4096 символов, без тела и с заголовками запроса не больше 32 КБ. Участок клиент → локальный прокси работает без TLS. Поэтому этот тест не подтверждает работу конкретного CDN, выпуск публичных сертификатов или скорость интернета.

Для проверки нового edge runtime выполните:

```bash
python tests/smoke_edge.py
```

Сценарий сам скачивает закреплённый официальный Xray и проверяет SHA256. Только загрузка бинарника и его контрольной суммы обращается в интернет. Остальной тест использует временные loopback-службы: TLS с явно доверенным тестовым сертификатом, XHTTP, TCP relay и SOCKS с паролем. Проверяются 1 000 000 байт отправки, 1 MiB получения, целостность данных и завершение временных listeners. Этот тест не проверяет физический Ethernet, публичный CDN или конкретный VPS.

## Проверка на VPS

Для проверки полной схемы нужны готовый CDN, домены и отдельный VPS. Для режима двух серверов нужен дополнительный exit.

1. Выполните `plan` и проверьте адреса, конфиги и порты до установки.
2. Выполните `deploy`. Убедитесь, что сертификаты выпущены, службы работают, а `nginx -t` и `xray run -test` завершаются успешно.
3. Проверьте автоматический подбор edge после установки. В `result/status.json` должны быть `endpoint_verified=true`, `vless_tunnel_verified=true`, выбранный `connect_address` и маршрут проверки. Для доказательства проводного пути нужен именно `route=ethernet`; `default` может проходить через активный VPN.
4. Выполните `check` и `repair-edge`. OPTIONS должен сохранять тело, включая пакет в 1 000 000 байт. Реальный Xray должен авторизоваться тем же UUID, передать данные с совпадением хешей и показать ожидаемый внешний IP origin либо exit. Установщик не поддерживает VPS за NAT с другим внешним адресом.
5. Импортируйте выданную ссылку или клиентский JSON в приложение с поддержкой XHTTP extra. Проверьте отправку и получение файлов, внешний IP и отказ с незарегистрированным UUID. В адресе должен быть выбранный edge, в SNI/Host — CDN-домен, в XHTTP — внешний `mode=packet-up`.
6. Запустите программу из новой папки без `deployment.json`, подключитесь к origin и проверьте восстановление доменов, пути, UUID и exit, если он используется. Выдача ссылок должна повторить edge-подбор без повторного ввода доменов.
7. Увеличьте количество UUID и проверьте работу старых и новых ссылок. Затем уменьшите количество: сохранённые UUID продолжают работать, удалённые больше не авторизуются. Повторная установка сохраняет оставшиеся UUID.
8. На тестовом CDN проверьте смену доменов и XHTTP-пути после подготовки DNS/CDN владельцем. При недоступном edge серверные настройки должны сохраниться, новые ссылки не выдаваться, а отрицательный статус не должен выдавать старые файлы за успешный результат.
9. На одноразовых VPS прервите обновление между exit и origin, затем продолжите его через меню. Сверьте сохранение UUID, серверные конфиги и состояние служб.
10. Проверьте продление сертификатов командой `certbot renew --dry-run`. Отдельно проверьте перечитывание сертификата службами и копирование на exit: тестовое продление не всегда запускает deploy-hook.

Для сравнения скорости используйте одинаковый клиент и направление, минимум три передачи файлов по 20–100 МБ в обе стороны для каждого профиля. Записывайте скорость и ошибки; меньший интервал сам по себе не доказывает прирост скорости.

## Проверка архива релиза

Пользовательский архив — `Source code (zip)` конкретного GitHub-релиза. Перед публикацией проверьте запуск из чисто распакованной папки: `run.cmd --version` на Windows, `bash run.sh --version` на Linux, затем `--help` и офлайн `plan` с демонстрационным конфигом. Запуск должен подготовить своё окружение и показать версию из тега.

В архив должны попасть `run.cmd`, `run.sh`, `bootstrap.py`, пакет, документация и метаданные зависимостей. В него не должны попадать `.venv`, `deployment*.json`, `known_hosts`, `result/`, VLESS-ссылки, секреты и результаты реальных серверных проверок. Архивы wheel/sdist не заменяют полный исходный архив для сценария запуска через `run.cmd`/`run.sh`.

## Границы совместимости

Установщик рассчитан на Ubuntu 22.04/24.04, amd64/arm64 и systemd. В прежней версии установщика установка и прямое подключение к origin проверены на Ubuntu 22.04 и 24.04 amd64. На Ubuntu 24.04 также проверены два UUID, передача по 1 000 000 байт с совпадением SHA256, выход в интернет через VPS, отказ незарегистрированному UUID и тестовое продление сертификата с deploy-hook.

На одном готовом ресурсе Yandex Cloud CDN проверены HTTPS, передача OPTIONS и полное VLESS-подключение к origin на Ubuntu 24.04: две учётные записи, целостность отправленных данных, выходной IP и отказ неизвестному UUID. Проверки прошли по двум сетевым маршрутам. Это функциональная проверка, а не измерение скорости или гарантия доступности всех узлов CDN.

Новый selector версии 0.2.0 пока не прошёл приёмку через реальный публичный CDN. Прежние результаты не заменяют отдельную приёмку автоматического edge-подбора, восстановления и управления UUID. Текущие сетевые результаты хранятся локально в `result/status.json`, а выполненные проверки конкретного выпуска перечисляются в его описании на GitHub.

arm64, два физических VPS и импорт в конкретные клиентские приложения требуют отдельной проверки. Работу через CDN нужно проверять отдельно для выбранного ресурса и сети пользователя: успешное прямое подключение к origin её не подтверждает. Успех локальных тестов не заменяет такую проверку.

## Проверка обновления программы

Тесты обновления используют локальные архивы и заглушку GitHub. Проверяйте стабильную версию, отказ/недоступность сервиса, согласие пользователя, SHA256 и состав манифеста, запрет traversal/symlink и конфликтов имён. Успешное обновление должно сохранить байты deployment, pending, backup, known_hosts, result и нестандартных пользовательских файлов; ошибка должна оставить исходную папку рабочей. Проверяйте приватность копий, отказ для Git checkout и изменённого кода. Обновление не должно запускать SSH или серверные операции.

Опубликованный release ZIP и его SHA256 проверяются отдельно после загрузки с GitHub. Юнит-тесты не подтверждают доступность GitHub у каждого пользователя или работу CDN на его сети.

## Подготовка выпуска с автообновлением

Зафиксируйте проверенные изменения и версию в Git. Выполните `python tools/build_release.py --output /path/to/release-assets` с новой пустой папкой назначения. Сборщик читает только Git HEAD: незакоммиченные файлы, локальные конфиги и `.venv` в архив не попадают. Версия пакета должна совпадать с `pyproject.toml`.

В GitHub Release с тегом `vX.Y.Z` загрузите оба файла: `cdn-xhttp-setup-vX.Y.Z.zip` и `cdn-xhttp-setup-vX.Y.Z.zip.sha256`. Манифест уже находится внутри ZIP. Публикуйте стабильный релиз после загрузки обоих assets; автоматический Source code ZIP сам по себе не подходит для механизма обновления. После публикации скачайте assets обратно, проверьте SHA256 и принятие архива `download_release()` из `cdn_xhttp.updates`.
